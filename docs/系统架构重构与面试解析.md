## 一、 核心范式抉择：为什么是 Workflow 而不是 ReAct？

在项目初期，我们面临了 Agent 底层架构的选择。
*   **被否决的方案（纯 ReAct）**：虽然 ReAct 赋予了大模型极高的自由度去思考（Thought）和行动（Action），但在强监管的政务场景或电商客诉场景下，大模型极易陷入**“工具调用死循环”**或产生**“不可控的幻觉操作”**（如乱派单、乱退款）。
*   **最终确立的方案（LangGraph StateGraph）**：采用有状态的图结构工作流（Workflow）。将原本黑盒的 Agent 拆解为明确的节点（预处理 -> 意图分类 -> 多路检索 -> 知识融合 -> MCP微服务调用）。
*   **架构收益（面试话术）**：“采用 LangGraph 实现了**SOP（标准作业程序）的确定性流转**。这不仅保证了政务/商业回复的合规性与可解释性，更使得我们在任意节点都能轻松插入‘人工审核（Human-in-the-loop）’或‘兜底降级’机制，这是企业级 Agent 落地的必然选择。”

## 二、 数据治理与 RAG 优化：解决“语义鸿沟”与 Token 灾难

由于政务数据（及电商规则）来源复杂，我们彻底摒弃了“大一统向量库”和“暴力切片”的业余做法，针对不同数据源实施定制化 ETL：

### 1. 《权责清单》Excel：Data-to-Text 语义序列化
*   **痛点**：结构化表格直接丢给 BGE-M3 向量化，属于**分布外数据（OOD）**，破坏了模型预训练时的自然语言注意力机制，导致用户口语化投诉（“大白话”）无法检索到政府法条（“法言法语”）。
*   **解法**：编写 Python 脚本，采用**基于提示模板的序列化（Template-based Serialization）**。将离散的表格字段拼接为包含强逻辑关联的主谓宾陈述句：
    *   *转换前*：`市城管局, 行政处罚, 占道经营`
    *   *转换后*：`【市城市管理行政执法局】的法定职责包含行政处罚：对占道经营的处罚。`
*   **收益**：巧妙地将“结构化匹配”降维为“非对称自然语言检索”，极大提升召回率，彻底替代了昂贵且难以维护的传统 TextCNN/BERT 模型微调。

### 2. 1.5 万条《历史案例》：降维打击与正则归一化
*   **痛点**：全量使用 LLM 做知识蒸馏成本过高（Tokenomics 问题）；且历史数据中充斥着“大渡口派出所”等基层单位，与《权责清单》的市本级标准架构严重错位（数据粒度不一致）。
*   **解法**：放弃 LLM 提炼，改用 Pandas 离线正则映射（Data Normalization）。利用核心业务关键词（如“交警”->“市公安局”），将区县基层单位**强行向上降维对齐**到标准市级单位。
*   **收益**：零 API 成本完成 1.5 万条数据清洗，保障了下游微服务调用的数据一致性。MVP 阶段只需抽样 500 条高质量数据进行 `【历史诉求】+【历史答复】` 拼接入库。

### 3. 《办事指南》Word 2003 XML：元数据感知切片 (MVP阶段暂缓)
*   **规划解法**：编写 BeautifulSoup 脚本剥离 XML 标签，按“受理条件”、“申请材料”等业务板块进行**Metadata-Aware Chunking**，并在切片前强制拼接“事项名称”作为全局上下文。
*   **收益**：解决传统 Chunking 导致的上下文断裂问题，单次检索 LLM Token 消耗量可降低 80% 以上。

## 三、 Pydantic 模型重构：主数据与脏数据的完美隔离

在分类器节点中，为了解决“用户非标输入”导致“下游 MCP 微服务调用失败”的致命 Bug，我们对数据模型进行了**“双字段解耦”**设计。

**核心代码备忘：**
```python
class GovRequestClassifiedResult(BaseModel):
    request_type: GovRequestType = Field(description="问政请求类型")
    
    # 1. 强约束的主数据 (Master Data) -> 用于底层系统路由和 MCP 接口调用
    target_city_department: str = Field(
        description="标准市级主管部门。必须基于《权责清单》推导，如'市公安局'。若无法确定填'市长热线办'。"
    )
    
    # 2. 弱约束的脏数据/上下文 (Dirty Data) -> 仅用于 LLM 最终话术生成，提供情绪价值
    mentioned_local_agency: Optional[str] = Field(
        default="", 
        description="用户实际提及的基层单位名称，如'纳溪区人社局'。未提及则为空。"
    )
```
*   **架构思考**：底层微服务要的是**绝对的稳定（市局兜底）**，而 C 端用户要的是**被倾听的体验（区县回应）**。这个 Pydantic 设计完美兼顾了系统鲁棒性与 AI 拟真度，是典型的电商“实体解析（Entity Resolution）”思维。

## 四、 LangGraph 状态机高阶编排：双路召回与情绪逃逸机制

### 1. 核心链路：并行双路召回 (Parallel Dual-Track Retrieval)
当分类器识别为【投诉/举报】意图时，弃用《办事指南》，并发查询两个 Milvus 集合：
*   **查《权责清单》**：寻找“法理依据”（定性归哪个市局管），内置 BGE-Reranker 并设定 `0.45` 阈值，低于阈值则阻断猜测。
*   **查《历史案例》**：寻找“历史判例”（看看以前类似纠纷怎么解决的）。
*   **融合生成 (Fusion Node)**：在 Prompt 中同时注入法理与判例，让大模型输出既严谨又具有同理心的安抚话术，随后调用 MCP 工具派发工单。

### 2. 交互健康度监控：情绪逃逸机制 (Escalation Router)
*   **设计背景**：抛弃不切实际的“生命危险报警”枚举，转而解决 AI 客服最痛的“死循环”问题。
*   **实现方式**：利用 LangGraph 的**条件边 (Conditional Edge)**。
*   **逻辑备忘**：
    ```python
    def intent_router_node(state: AgentState):
        # 监控对话深度 (Frustration Counter)
        if len(state.get("messages",[])) >= 6: 
            return "escalation_route" # 触发熔断逃逸
        return "normal_retrieval_route"
    ```
*   **兜底动作**：当触发逃逸时，跳过所有 RAG 检索，直接调用 `create_gov_work_order` 生成高优工单，并安抚用户等待人工介入。这体现了极强的**风控意识与系统边界控制能力**。

## 五、 框架标准化：全面拥抱 LangChain/LangGraph 原生生态

为了去除“学生气”，向企业级代码靠拢，我们明确了以下重构动作（删掉冗余的手写轮子）：

1.  **废弃手写 Memory**：全面接入 LangGraph `MemorySaver` 检查点机制，实现优雅的会话状态持久化。
2.  **废弃手写 JSON 解析器**：分类器全面接入 `llm.with_structured_output(GovRequestClassifiedResult)`，利用大模型 Function Calling 强约束输出。
3.  **废弃手写 Tool 路由**：全面采用 LangChain `@tool` 装饰器 + `llm.bind_tools()` + LangGraph 预置 `ToolNode`，将复杂的跨语言 MCP 调用安全地交接给框架底层引擎。
